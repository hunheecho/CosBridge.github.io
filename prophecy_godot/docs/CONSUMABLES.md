## 1. 무료 휴식권 40 → 100 (사용자 결정)

| 항목 | 값 | 어디에 |
|---|---|---|
| 정본 | `data/world.json` → `shop.merchantService.free_rest` = **100** | 코드에 숫자를 두지 않는다 |
| 재고 | `PRun.refresh_stock` → `run.merchant.servicePrice` | 정본을 그대로 읽는다(예전 하드코딩 40 제거) |
| 표시 | 상점 카드 · 거점 방문 상인 줄 · 행동 목록 | 셋 다 `servicePrice`를 읽는다 |
| 거래 | `PRun.buy_merchant_service` | 금화가 정확히 그 값만큼 줄고 권 1장이 생긴다 |

**'무료'의 뜻**: 쓸 때 **시간이 들지 않는다**(보통 휴식은 시간 1칸). 사는 것은 유료다.
화면에는 "구매 유료 · 쓸 때 시간 0칸"과 구매값 100을 같이 적는다.

**공짜로 받은 권에는 청구하지 않는다.** 사건 보상(`PEvents`)이 주는 휴식권은 `run.services.free_rest`에 그냥 들어가고,
`PRun.rest`는 보유한 권을 쓸 뿐 금화를 보지 않는다. 검사로 고정: `prep_shop_tests` "보상으로 받은 무료 휴식권: 금화 0 · 시간 0칸".

## 2. 상점: 유료 새로고침 · 잠금

| 항목 | 값 | 근거 |
|---|---|---|
| 값 | `60 × 1.5^(오늘 한 횟수)` → **60 / 90 / 135** | 장비 1개(120~140)보다 싸게 시작해서 연속하면 비싸진다 |
| 하루 상한 | **3회** | 하루 최대 285금 흡수 |
| 잠금 | **2칸**(장비 2 + 기술 1 중에서), 값 없음 | 원하는 것을 지키고 나머지만 다시 뽑는다 |
| 초기화 | **다음 날 아침**(`PRun.end_day` → `refresh_stock`) | 횟수·값·잠금이 모두 0으로 |

**복제가 없는 이유(검사로 고정)**
- 이미 산 칸은 `stock.sold`에 남고, 새로고침해도 그 자리를 지킨다 → 같은 장비를 두 번 살 수 없고 산 물건이 되살아나지 않는다.
- 후보 풀에서 `owns_equip`인 장비는 애초에 빠진다.
- 새로고침 실패(한도 초과·금화 부족)는 회차를 **전혀** 바꾸지 않는다(JSON 동일 검사).
- `stock.refresh.count` / `stock.locked` / `stock.sold`가 저장에 들어가므로 재접속해도 횟수가 되돌아가지 않는다.
- 새로고침 시드는 `stock_seed + 횟수×7919` — 저장 필드에서만 나오므로 재접속 재추첨이 없다.

방문 상인 물건은 새로고침 대상이 아니다(하루 1회 확정).

## 3. 장비: 역할과 막 게이팅

장비 12종에 `role` / `roleName` / `minAct`를 붙였다(효과·이름·설명은 그대로 — 기존 검사 불변).

| 부위 | 1막부터 | 2막부터 |
|---|---|---|
| 무기 | 사냥꾼의 검(정예 상대) · 개척자의 창(다수 처리) | 잔불검(지속 피해 연계) · 시간술사의 지팡이(Q 연계) |
| 갑옷 | 여행자의 경갑(접근·위치) · 수호자의 갑옷(보호막) · 생명력의 외투(체력) | 원정대의 갑옷(회복) |
| 방패 | 철벽 방패(큰 타격 방어) · 비상 방패(보호막) | 시전자의 방패(E 연계) · 시간의 방패(Q 연계 방어) |

- 1막에도 부위마다 후보가 2개 이상이고, 2막에서 부위마다 새 역할이 열린다(같은 장비의 상위 수치 반복이 아니다).
- 상점·상인 재고 풀이 `PRun.equip_act_ok`로 걸러진다. 막을 알 수 없는 회차(trio·시험실)는 제한하지 않는다 — 기존 동작 그대로.
- 상점 카드에 "역할 · <이름>" 줄을 넣어 같은 부위 후보를 무엇으로 고를지 먼저 보이게 했다.

새 장비를 **더 넣지는 않았다**. 이유와 제안은 보고의 "담당 밖 파일에 필요한 변경"에 적었다
(`PCatalog.equipment().size() == 12`을 못 박은 검사가 `tests/meta_tests.gd`·`tests/port_tests.gd`에 있고 둘 다 이 작업의 수정 대상이 아니다).

## 4. 출격 준비물 (전투 단축키를 늘리지 않는 방식)

거점에서 **1개만** 골라 두면 다음 전투가 시작될 때 저절로 쓰인다. 새 조작이 없다.

| id | 이름 | 값 | 역할 | 효과(시험값) |
|---|---|---:|---|---|
| `guard_charm` | 수호 부적 | 45 | 보호막 | 전투 시작 시 보호막 **25** |
| `shatter_oil` | 파쇄 기름 | 60 | 방어 자세 상대 | 막고 있는 적의 정면 감소 배율에 **하한 0.35** |
| `cleanse_incense` | 정화 향 | 45 | 해로운 지면 효과 | 거미줄·빙판 감속 **절반**, 포자·붕괴 바닥 피해 **-30%** |
| `hunter_seal` | 사냥꾼의 인장 | 55 | 정예 상대 | 정예·보스 직접 피해 **+10%** |
| `relief_pouch` | 응급 약낭 | 50 | 회복 | 체력 **30% 이하**가 되면 체력 **18** 회복(전투당 1회) |

**규칙**
- 가방 **3개**까지, 같은 종류 **2개**까지, 장착은 **1개**. 중첩 없음.
- **소모 시점**: 전투 입장. 빌드 계산 → `CombatState` 생성 → 소모, 이 순서라 그 전투에는 들어가고 가방에서는 한 번만 빠진다.
- **같은 출격에서 더 깊이 들어가는 다음 전투로 자동 연장되지 않는다.** 다시 고르지 않으면 아무것도 쓰지 않는다.
- **입장 전 해제·교체는 소모가 아니다.** 가방·금화가 그대로다(JSON 동일 검사).
- 상점 할인권(`shop_discount`)은 준비물에 **적용하지 않는다**(할인 대상은 장비·제작).

### 4.1 파쇄 기름과 방패 감소의 관계 (중복 계산 금지)

`PEnemiesNew.shield_mult`는 여러 방어 효과가 겹쳐도 **곱하지 않고 가장 강한 하나(min)만** 쓴다. 이 규칙은 그대로 둔다.
기름은 그 `min`이 낸 **결과에 하한을 둘 뿐**이다 — 곱하지도, 따로 한 번 더 적용하지도 않는다.

```
m = min(방패 정면, 깃발 방어)          ← 기존 규칙 그대로(한 번만)
m = max(m, 0.35)                        ← 파쇄 기름(하한, 한 번만)
```

| 상대 | 기름 없음 | 기름 있음 | 뜻 |
|---|---:|---:|---|
| 방패병 정면(`frontMult` 0.15) | 0.15 (85% 감소) | **0.35** (65% 감소) | 정면 피해가 2.3배 |
| 정예 검사 방어 자세(`guardMult` 0.0) | 0.0 (완전 차단) | **0.35** (65% 감소) | 완전 차단이 풀린다 |
| 군단 기수 깃발 | 0.7 등 | 그대로 | 이미 하한보다 크다 |
| 옆·뒤, 바닥·추가·기술·지속 피해 | 1.0 | 1.0 | 기름이 붙지 않는다 |

**정면 맞다이를 되살리지 않는다**: 하한을 둬도 정면은 여전히 65% 감소다. 옆·뒤로 도는 쪽이 계속 낫다.
기름은 "방패를 뚫는 열쇠"가 아니라 "방패 상대의 벽을 낮추는 준비"다.

### 4.2 정화 향이 무엇에 걸리는가 (실제로 있는 상태만)

이 게임에서 **플레이어에게 붙는 지속 상태는 전부 바닥 효과**다. 화상·출혈·냉기(`burn`/`bleed`/`chill`)는 **적에게만** 붙는다
(`CombatState.spawn_enemy`의 적 필드). 그래서 향은 그것들을 지운다고 적지 않는다.

| 실제로 있는 것 | 어디서 | 향의 효과 |
|---|---|---|
| 거미줄(`web` 지대, 걷기 ×0.5) | 거미 | 감속 폭 절반(×0.5 → ×0.75) |
| 빙판(`ice` 지대, 걷기 ×0.6) | 서리 추적자 | 감속 폭 절반(×0.6 → ×0.8) |
| 포자 구름(`spore` 지대, 지속 피해) | 포자 개체 사망 | 지대 피해 -30% |
| 붕괴 바닥(`hazard` 지대, 지속 피해) | 위험 조건 임무 | 지대 피해 -30% |

겹쳐도 가장 강한 하나만 보는 기존 규칙(`web = min(...)`)은 그대로다.

> **사용자 확인 필요**: 지시에는 "해로운 상태 **지속** 감소"라고 적혀 있으나, 엔진에는 플레이어에게 시간이 걸리는 상태가
> 없고 바닥 지대만 있다. 그래서 "지대가 나를 붙잡는 **정도**"를 줄이는 형태로 만들었다. 지대의 **수명**을 줄이는 쪽이
> 뜻에 더 맞다면 바꿀 수 있다(그 경우 지대가 적에게도 짧아지므로 다른 규칙이 된다).

### 4.3 겹치는 장비와의 관계

| 준비물 | 겹치는 장비 | 어떻게 처리하나 |
|---|---|---|
| 수호 부적(보호막 25) | 수호자의 갑옷(15) · 월광 갑옷(20) | 빌드의 `shield`에 **더한다**. `equip.startShield`에는 넣지 않는다 — 월광 갑옷의 재생 상한이 그 값을 읽기 때문에 거기 더하면 갑옷 효과까지 커진다 |
| 사냥꾼의 인장(+10%) | 사냥꾼의 검(+15%) | 같은 칸(`equip.eliteDirect`)에 **더한다**. 전투는 `(1 + eliteDirect)`를 한 번만 곱하므로 곱 중복이 없다(0.25) |
| 응급 약낭(체력 18) | 비상 방패(보호막 20) | **다른 칸**(`lowHeal` vs `lowShield`). 둘 다 있으면 각각 1회 발동한다 — 하나의 발동 표시를 나눠 쓰지 않는다 |
| 파쇄 기름 | 없음 | `shield_mult` 결과의 하한 1회 |
| 정화 향 | 없음 | 지대 감속·피해에 1회 |

## 7. 게임에 실제로 붙이려면 필요한 훅

규칙·데이터·화면·검사는 이 작업에서 끝났다. 아래 다섯 곳은 이 작업의 수정 대상이 아닌 파일이라 손대지 않았다.
정확한 위치와 줄은 보고에 적었다. 훅이 붙기 전까지의 상태:

| 준비물 | 지금 상태 |
|---|---|
| 수호 부적 | **그대로 작동**(빌드의 시작 보호막을 통해) |
| 사냥꾼의 인장 | **그대로 작동**(`equip.eliteDirect`를 통해) |
| 파쇄 기름 | 값은 계산되지만 전투가 아직 묻지 않는다 → `enemies_new.gd` 1곳 |
| 정화 향 | 값은 계산되지만 전투가 아직 묻지 않는다 → `combat_state.gd` 2곳 |
| 응급 약낭 | 값은 계산되지만 전투가 아직 묻지 않는다 → `combat_state.gd` 1곳 |
| 소모(전투 입장) | 검사는 같은 순서를 재현한다 → `flow.gd` 2곳 |

## 8. 부활 물약 (2026-09-09 사용자 확정)

사망 = 회차 종료 규칙이 들어오면서 생긴 **유일한 대비책**이다. 자세한 규칙·경계·화면 함수는 `docs/DEATH_AND_ECONOMY.md`.
여기서는 "가방에 들어가는 물건"으로서의 규칙만 적는다.

| 항목 | 값 | 어디에 |
|---|---|---|
| 정본 | `data/consumables.json` → `revive` (id `revive_potion`) | 코드에 숫자를 두지 않는다 |
| 값 | **220** (시험값) | 회복약 35·준비물 45~60보다 훨씬 크다 — 회차를 한 번 더 사는 값 |
| 회복량 | 부활 시 **최대 체력의 25%**(`hpFrac`) | 사용자 확정 |
| 가방 상한 | **2개**(`rules.reviveCarryMax`) | 준비물(3)·회복약(3)과 **별도 계정**이라 서로의 자리를 먹지 않는다 |
| 하루 구매 상한 | **없다** | 회복약과 달리 값 자체가 상한 역할을 한다 |
| 사용 | **자동**(쓰러졌을 때 보유하고 있으면 한 개) | 쓸지 묻지 않는다. 거점에서 손으로 쓰는 버튼이 없다 |
| 진열 | 상점에 늘 있다(준비물 진열 3칸과 별도) | 하루 시드 추첨 대상이 아니다 — 필요할 때 살 수 있어야 하는 물건이라서 |

**행동 목록**: `PFlow.actions(run)`의 `buy_revive`(`kind` 도 `buy_revive`, `data = { id, price, have }`).
회차 봇도 이 항목으로만 산다(`PRunBot._shop_bot`) — 사람 플레이 규칙 회차에서만, 1개까지, 예비 금화를 남기고.

**소모 함수**: `PConsumables.consume_revive(run) -> bool`. **`PRun.settle_death`만 부른다.**
다른 어디에서도 부활 물약을 빼지 않으며, 스냅샷 복구(`PConsumables.restore`)로 되살아나지 않는다(사망 경로는 스냅샷을 지운다).
