# 손가락 스크롤 (PTouchScroll)

폰에서 목록을 손가락으로 넘기는 장치. 정본은 `scripts/game/ui/touch_scroll.gd` 하나다.
회귀 시험은 `tests/scroll_tests.gd`(스위트 `scroll_tests`).

## 한 곳만 고치면 전부 고쳐지는 이유

화면 14개(상점·장비·대장간·통계·기록·보상·사건·결과·거점·제목·시작 선택·패배·보스 결과·영구 성장)가
모두 `PScreen`(`scripts/game/screens/screen_base.gd`)을 상속한다. `PScreen.setup()`이 본문 스크롤을
만들면서 **거기에 `PTouchScroll`을 하나 붙인다.** 화면 쪽 코드는 아무 것도 하지 않는다.

```
PScreen.setup()
  scroll = PUi.scroll()
  touch_scroll = PTouchScroll.attach(self, scroll)   ← 화면마다 하나. 이게 전부다
  touch_scroll.blocked = confirm_open                ← 확인 창이 열려 있으면 새 끌기를 시작하지 않는다
```

다른 곳(3택 창처럼 `PScreen`이 아닌 스크롤)에도 같은 줄 하나로 붙일 수 있다.

## 무엇이 잘못돼 있었나 (2026-09-09 계측)

친구가 폰으로 플레이하며 남긴 말: **"이거 또 스크롤 / 한 칸씩밖에 왜 안 되냐"**.

### 진짜 원인 — 우리가 밀어 넣은 취소 사건이 우리 끌기를 죽였다

끌기로 판정하는 순간 눌려 있던 버튼에 취소를 보낸다(그래야 "넘기려다 실수로 팔았다"가 안 생긴다).
그 취소를 `get_viewport().push_input()`으로 밀어 넣었는데, **그 사건은 곧바로 우리 `_input`으로 되돌아온다.**
옛 코드는 그것을 사람이 손을 뗀 것으로 읽고 `_drag_id = -1`로 지웠다. 그 뒤부터 같은 손가락의 끌기는
전부 `d.index != _drag_id`에 걸려 버려졌다.

계측(헤드리스, 옛 코드 그대로):

```
touch pressed idx=0
drag idx=0 (_drag_id=0)
  → 취소 사건 밀어넣기
  touch pressed=false idx=0 canceled=true     ← 되돌아온 우리 사건
  → 취소 사건 뒤: _drag_id=-1  _dragging=false ← 여기서 끌기가 죽는다
  → scroll 0 에서 299 로                        ← 이 한 번만 적용된다
drag idx=0 (_drag_id=-1) → 무시
drag idx=0 (_drag_id=-1) → 무시
drag idx=0 (_drag_id=-1) → 무시
```

**한 번 누를 때마다 딱 한 사건**만 움직였다. 그게 "한 칸씩"이다. 손을 떼고 다시 눌러야 한 칸 더 갔다.
버튼이 빽빽한 상점에서 특히 심했다 — 카드 사이 빈 곳이면 Godot 내장 터치 스크롤이 대신 받아 주지만,
버튼 위에서 시작하면 내장도 못 받아서 정말 아무 것도 안 움직였다.

### 두 번째 원인 — 1px 미만 이동이 통째로 버려졌다

옛 식은 `scroll_vertical = int(scroll_vertical) - int(relative.y)`였다.
`scroll_vertical`은 정수라 사건마다 잘라 넣을 수밖에 없었는데, 그러면 **소수가 매번 사라진다.**

| 끌기 | 참값 | 옛 식 |
|---|---|---|
| 0.4px씩 10번 | 4px | **0px** |
| 1.6px씩 10번 | 16px | 10px |

폰은 화면 갱신(60Hz)보다 손가락을 더 자주 읽고(120~240Hz), 화면 배율(`canvas_items`·`expand`,
설계 960x640) 때문에 한 사건의 이동량이 더 작아진다. 천천히 끌수록 아예 안 움직였다.

### 관성은 원래 없었다 (의심했지만 이것이 원인은 아니다)

`set_input_as_handled()`가 Godot `ScrollContainer`의 내장 터치 스크롤을 가로채는 것은 사실이다.
다만 내장 터치 스크롤은 `DisplayServer.is_touchscreen_available()`이 참일 때만 도는 것이라
**PC·헤드리스에서는 애초에 돌지 않는다**(계측으로 확인: PScreen 없이 같은 끌기를 넣어도 0px).
그러니 PC에서 잃은 것은 없고, 폰에서는 잃는다. 그런데 내장에는 **12px 문턱이 없어서** 살짝만 밀려도
스크롤이 시작된다 — 우리가 일부러 대신하기로 한 것이다. 그래서 되살리는 대신 **직접 관성을 만들었다.**

## 지금 구조

`PTouchScroll`(Node)이 `ScrollContainer` 하나를 맡는다.

- **소수점 이동.** 자리를 float `_pos`로 들고, 화면에는 반올림한 정수만 넣는다.
  남는 소수는 `_pos`에 남아 다음 사건·다음 프레임으로 이어진다.
- **관성.** 손을 떼는 순간의 속도 = **마지막 0.1초 동안 실제로 움직인 거리 ÷ 그 시간**(안드로이드
  VelocityTracker와 같은 방식). 그 속도로 미끄러지다 마찰로 멎고, 경계에서는 그 자리에 선다(튕기지 않는다).
  떼기 직전 0.12초 동안 손가락이 멈춰 있었으면 던지지 않는다.
- **탭과 끌기.** 12px을 넘겨야 끌기다. 넘는 순간 눌려 있던 버튼에 취소를 보낸다.
  누름 사건은 절대 삼키지 않아 평범한 탭은 그대로다.
- **되돌아온 취소를 무시.** `_in_cancel` 동안 들어오는 사건은 우리 것이므로 상태를 건드리지 않는다.
  취소는 `push_input(c, true)`(뷰포트 좌표)로 넣는다 — 옛 코드는 좌표를 한 번 더 변환시켜
  (100, 230)을 (22500, 40500)으로 보냈다.
- **여러 손가락.** 먼저 닿은 손가락이 끝까지 스크롤을 쥔다. 다른 손가락이 눌려도 뺏기지 않는다.
- **화면 전환.** `PScreen.on_enter()`가 `stop()`을 부른다. 화면이 안 보이게 되면 `step()`이 스스로 멈춘다.
- **PC.** `PLayout.is_touch()`가 거짓이면 사건을 하나도 삼키지 않는다. 마우스 휠은 `ScrollContainer`가 그대로 맡는다.

### 시험값 (사람 손으로 맞춰야 하는 값. 규칙과 무관하다)

| 이름 | 값 | 뜻 |
|---|---|---|
| `DRAG_START_PX` | 12.0 px | 이만큼 움직여야 탭이 아니라 끌기 |
| `MAX_SPEED` | 3000 px/초 | 관성 최대 속도(화면 하나가 640px) |
| `FRICTION` | 2000 px/초² | 마찰. 최대 속도에서 약 1.5초·2250px 미끄러진다 |
| `STOP_SPEED` | 8 px/초 | 이보다 느려지면 멈춘다 |
| `VEL_WINDOW` | 0.10초 | 뗄 때 '마지막 이만큼' 동안의 이동으로 속도를 낸다 |
| `VEL_IDLE` | 0.12초 | 떼기 전에 이만큼 멈춰 있었으면 던지지 않는다 |

모의 계측(`scroll_tests`): 프레임마다 30px씩 네 번 끌고 떼면 **1773px/초 → 801px 더 미끄러진다.**
프레임마다 1px씩 끌고 떼면 **67px/초 → 2px.**

## 실제 게임 화면에서 잰 값 (모의 손가락, 창 1366x640)

폰 가로가 실제로 보는 것과 같은 뷰포트(1366x640)로 게임을 띄우고, **똑같은 96px flick**
(8px짜리 끌기 사건 12개를 6프레임에 나눠 넣고 뗀다)을 넣어 잰 값이다.

| 화면 | 목록 길이(max) | 옛 코드 | 지금 |
|---|---|---|---|
| 상점 | 1218px | **8px** | 뗄 때 88px → 멎을 때까지 **1119px** |
| 장비 | 446px | **8px** | 뗄 때 88px → **446px**(끝에서 멈춤) |
| 대장간 | 59px | **8px** | **59px**(끝에서 멈춤) |

옛 코드가 어느 화면에서나 정확히 8px인 것이 위에서 말한 "한 사건만 먹고 죽는다"의 증거다
(첫 8px 사건은 12px 문턱 아래라 안 움직이고, 두 번째 사건 하나만 적용된 뒤 끝났다).

캡처: `docs/captures/touch_scroll/<화면>_a_start_<before|after>.png`(끌기 전) ·
`<화면>_b_end_<before|after>.png`(멎은 뒤).

### 탭과 끌기가 갈리는지도 실제 화면에서 확인했다

상점의 `판매 +70` 버튼 위에서:

- 그냥 탭 → **판매 확인 창이 열린다**(탭이 살아 있다).
- 같은 버튼에서 시작해 끌기 → **확인 창이 열리지 않고** 목록만 183px 넘어간다.

즉 "넘기려다 실수로 팔았다"는 생기지 않는다. 창이 있는 실행에서만 확인할 수 있다 —
헤드리스는 터치를 GUI로 전달하지 않는다.

## 건드리면 안 되는 것

- **12px 문턱과 버튼 누름 취소.** 없애면 "넘기려다 실수로 팔았다"가 다시 생긴다(친구 보고, KD-8).
- **보던 자리 유지.** `PScreen.clear_all()`의 `_keep_scroll` + `_restore_scroll`.
  상점에서 '팔기'를 눌러도 맨 위로 튀지 않게 하는 것이다. `scroll_tests` K4·K5가 지킨다.
- **누름 사건을 삼키지 않는 것.** 삼키면 탭이 전부 죽는다.

## 실제 브라우저에서 잡은 것 (2026-09-09, 내보낸 웹 빌드 · 진짜 크롬)

여기까지의 숫자는 전부 헤드리스 모의였다. 내보낸 웹 빌드를 로컬 서버(127.0.0.1)에 띄우고
**진짜 크롬**을 폰 가로 크기(CSS 640×360 · 화면 배율 2 → 물리 1280×720, 캔버스 1137×640)로 맞춰
터치 입력을 실제로 보내 봤다. 목록이 움직인 양은 화면 픽셀(스크롤 막대 손잡이 자리)에서 직접 읽었다.

### 관성이 사실상 없었다

빠른 쓸기 뒤 목록이 **한 px도 더 가지 않았다**(1.5초 동안 자리 155.6 그대로).
엔진 안 로그로 확인한 속도 변화:

```
DBG stepdrag vel=520      ← 손가락이 움직인 프레임
DBG stepdrag vel=182      ← 사건 없는 프레임 → 0.35배
DBG stepdrag vel=63.7     ← 또 0.35배
DBG stepdrag vel=22.3     ← 또 0.35배
DBG stepdrag vel=527.8    ← 다음 사건이 그제야 도착
DBG lift    vel=171       ← 뗄 때 남은 값
```

원인: 속도를 **프레임마다** 재고 지수 평활(0.65)을 걸었다. 브라우저는 화면 갱신과 터치 표본의
주기가 달라 끌기 도중에도 사건 없는 프레임이 늘 섞이는데, 그런 프레임마다 속도가 0.35배로 죽었다.
헤드리스 모의는 프레임마다 사건을 하나씩 넣었으므로 이 상황이 만들어지지 않아 통과했다.

고친 방식은 위 '지금 구조'의 관성 항목이다. 회귀는 `scroll_tests` L절(사건 없는 프레임을 일부러 섞는다).

### 고친 뒤 실제 브라우저 계측 (상점, 목록 길이 1457 캔버스 px)

| 동작 | 손가락 이동(CSS px) | 목록 이동(캔버스 px) |
|---|---|---|
| 짧고 느린 끌기 | 30(15프레임) | **52.9** |
| 긴 끌기(끝에서 멈췄다 뗌) | 230(23프레임) | **370.5** |
| 빠른 쓸기 | 150(7프레임) | **675.8** (뗀 뒤 관성만 **321.6**) |
| 역방향(아래로) | 120(12프레임) | **-191.4** |
| 위 경계에서 더 끌기 | 150 | **0** |
| 아래 경계에서 더 끌기 | 150 | **0** |

- 관성 도중 **새 터치로 멈춤**: 그 자리에서 0px. 손을 안 댔으면 105.8px 더 갔을 자리였다.
- **화면을 나갈 때 관성 해제**: 미끄러지는 중에 '거점으로'를 눌렀더니 다음 화면은 900ms 동안 픽셀 차이 0,
  상점으로 되돌아오면 자리 0.
- **구매 오입력 방지**: '회복약 구매' 버튼 **위에서 시작한 끌기** → 목록 195.4px 이동, 금화 60 그대로.
  같은 버튼을 그냥 **탭** → 금화 60 → 25(실제 구매), 보던 자리 1038.1 유지.

## 아직 못 한 것

- **실기(안드로이드 폰) 확인.** 위 숫자는 **데스크톱 크롬**을 폰 크기로 맞춰 잰 것이다.
  실제 브라우저이긴 하지만 실제 폰은 아니다(손가락 굵기·터치 표본 주기·기기 성능은 확인하지 못했다).
- 빠른 쓸기처럼 **속도가 중요한 동작**은 CDP 입력이 한 사건당 74ms나 걸려 재현할 수 없어,
  페이지 안에서 프레임마다 하나씩 만든 터치 사건으로 쟀다(탭·경계·버튼 위 끌기·구매 오입력은 CDP 입력).
- 설정 창·3택 창이 떠 있는 동안에도 화면의 손가락 스크롤이 살아 있다.
  (화면 자신의 확인 창은 `blocked`로 막았다. 바깥 오버레이는 `PTouchScroll.enabled = false`로 끌 수 있게
  자리는 만들어 뒀지만 `main.gd`에서 아직 끄지 않는다.)
- 3택 창(`choice_overlay.gd`) 안의 스크롤에는 아직 안 붙였다. 붙이려면 `attach` 한 줄이면 된다.
